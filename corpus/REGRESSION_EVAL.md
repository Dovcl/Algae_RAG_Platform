# 챗봇 답변 회귀 평가

프롬프트·검색·생성 모델을 바꿀 때 같은 개발 질문으로 답변까지 생성해, 알려진 오류가 재발했는지 확인한다. **이 질문과 자동 검사 통과 수를 논문 성능 수치로 사용하지 않는다.** 연구실의 `질문지_*.xlsx` 60문항과 답변은 읽거나 가져오지 않았다.

## 파일 구성

- `corpus/regression_cases.json`: 버전 관리할 고정 개발 질문 49개와 기대 조건. 검색 개발 질문 22개를 모두 유지하고, 개념 5개·지점 확인 5개·지점 및 자료 시나리오 7개·잘못된 전제와 지시 2개·개념/공식 지침 경계 1개, 일반 원리 7개를 포함한다.
- `backend/scripts/eval_regression.py`: 생성·자동 검사·두 결과 비교·Markdown 보고서 생성. 새 의존성 없이 표준 라이브러리와 기존 앱 의존성만 사용한다.
- `backend/tests/test_eval_regression.py`: 잘못된 숫자 일치, 구간 값 뒤바뀜, 실제로 인용하지 않은 출처, 잘린 저장 파일 등 검사기 자체의 오류를 확인한다.
- `data/eval/`: 답변·원본 출력·실제 프롬프트·근거·검사 결과. Git에서 제외되어 있다.

## 기준값의 출처

2026-11-01에 로컬에 고정된 `DOC02_algae_alert_manual_2025-08.pdf`의 PDF 34쪽(인쇄 30쪽), **표 6**을 텍스트와 페이지 이미지로 대조했다. 문서의 표를 기준으로 하며 본문에 한 구간의 값만 있는 문장을 다른 구간에 확대 적용하지 않는다.

- 상수원: 관심 1,000 이상 10,000 미만, 경계 10,000 이상 1,000,000 미만, 조류대발생 1,000,000 이상, 해제 1,000 미만.
- 친수활동: 관심 20,000 이상 100,000 미만, 경계 100,000 이상, 해제 20,000 미만. 별도 조류대발생 행은 없다.
- 각 행은 2회 연속 채취 조건이다. 강우 예보 등 기상상황을 고려해 발령·해제하지 않을 수 있다는 비고도 있다. 숫자만으로 실제 발령 상태를 확정할 수 없다.

제품의 모델 단계(0~4)와 공식 경보 단계는 다르며, 전처리·단계 분류는 이 평가에서 수정하지 않는다.

## 실행

프로젝트 루트에서 실행한다. 먼저 기존 평가가 실행 중인지 확인한다. **Ollama 평가는 동시에 실행하지 않는다.** 브라우저에서 챗봇 질의를 동시에 보내는 것도 피한다.

```bash
docker compose top backend
mkdir -p data/eval
docker compose exec -T -e PYTHONPATH=/code backend python scripts/eval_regression.py \
  < corpus/regression_cases.json \
  > data/eval/run-01.jsonl \
  2> data/eval/run-01.log
```

이미 실행 중인 개발 환경을 사용한다. 로컬 venv에서 앱 서버나 평가 생성을 직접 실행하면 컨테이너 내부 DB에 접속하지 못한다. 컨테이너의 `/data`는 읽기 전용이므로 **stdout을 호스트 파일로 저장**한다. 코드 수정 없이 같은 설정의 평가를 2~3회 반복하려면 `run-02`, `run-03`처럼 매번 다른 이름을 사용한다. 기존 결과 파일을 덮어쓰지 않는다. 모델 요청이 오래 걸리므로 별도 터미널이나 작업 세션에서 실행하고 다른 터미널에서 진행을 본다.

```bash
tail -f data/eval/run-01.log
```

`LLM_PROVIDER=ollama`, `PREDICT_BACKEND=precomputed`와 ready 상태의 문서 컬렉션이 필요하다. 스크립트는 설정을 임의로 바꾸지 않는다. `.env`를 열거나 출력하지 않고 앱에서 로드한 설정 중 모델·검색·생성 옵션의 허용 목록만 기록한다. 모델 다운로드·패키지 설치·마이그레이션·자료 적재·제품 코드 변경은 하지 않는다. `build_answer`를 직접 호출하므로 채팅 기록 테이블에도 새 대화가 쌓이지 않는다.

## 결과 형식과 중단 복구

JSONL은 한 줄이 하나의 완전한 JSON이다.

1. `type=run`: UTC 시작 시각, 모델과 모델 digest, 임베딩 모델, 컬렉션, corpus/프롬프트/질문/검사기/제품 소스 해시, 생성 옵션, 컨테이너 이름, Python 버전.
2. `type=result`: 문항 ID·질문·기대 조건·실제 경로·시간·실패 이유·최종 답변·조치·근거 전체·한계·LLM 원본 출력·실제 프롬프트·구조화 수치·조회한 관측 날짜.
3. `type=summary`: 전체 통과 수, 문항 수, 종료 시각.

각 문항이 끝날 때마다 flush한다. 중간에 멈춰도 이미 완료된 문항은 남는다. 보고서/비교 기능은 마지막 줄만 잘렸으면 그 줄을 제외하고 읽으며, 중단된 실행임을 표시한다. 중간 행 손상은 오류로 처리한다. 미실행 문항을 통과로 간주하지 않는다. **중간부터 자동 이어 실행하는 기능은 없으며**, 재실행할 때는 다른 이름으로 전체를 실행한다.

문항의 `LlmError`·검색/DB 오류는 실패로 저장하고 다음 문항을 실행한다. DB 세션은 문항별로 분리하고 실패 시 rollback한다. 예외 원문의 URL이나 접속 정보는 남기지 않는다. `build_answer`가 예외를 던지면 반환값이 없으므로 그 문항의 원본 출력·입력은 확보하지 못할 수 있다. 정상 반환 문항은 둘 다 남긴다.

120초는 **완료 후 판정하는 회귀 검사 상한**이다. 스크립트가 120초에 Ollama 생성을 강제로 취소하지 않는다. 제품의 `llm_timeout`을 그대로 사용하며, 시간 초과 뒤 서버에서 이전 생성이 계속되는 상황도 가능하므로 시간 비교는 같은 장비·비슷한 부하에서 해석한다. 컨테이너 이름은 실제 맥/서버 장비의 동일성을 보장하지 않는다.

명령이 정상 종료되어도 일부 문항이 실패할 수 있다. CI의 성공 여부 대신 `summary`와 보고서의 실패 목록을 확인한다.

## 보고서와 이전 결과 비교

호스트에서 Python 3.11로 실행한다. 생성 실행과 달리 앱·DB·Ollama 연결이 필요 없다.

```bash
python3.11 backend/scripts/eval_regression.py --report data/eval/run-01.jsonl \
  > data/eval/run-01.md
python3.11 backend/scripts/eval_regression.py --compare \
  data/eval/run-01.jsonl data/eval/run-02.jsonl \
  > data/eval/run-01-vs-02.txt
```

기존 `baseline.json` 같은 단일 JSON 결과도 읽는다. 다만 이전 검사기는 숫자 부분 일치나 실제 본문 미인용 등을 놓쳤으므로 새 검사기의 점수와 같은 뜻이 아니다. 질문/검사기 해시가 바뀌면 통과 수를 곧바로 회귀로 해석하지 않는다. 개별 문항의 조건 해시가 다르면 그 문항의 회귀 판정을 제외한다. 삭제된 문항이나 실행되지 않은 문항도 표시한다. 답변 변경 수는 본문뿐 아니라 조치·근거·한계 변경도 센다.

`통과→실패`는 나빠짐, `실패→통과`는 좋아짐, `실패→다른 실패`는 실패 내용 변경으로 표시한다. 첫 실행 하나만으로 이전 버전보다 개선/악화됐다고 주장할 수 없다.

## 자동 검사의 범위

- 기대 경로, 오류, 문항별 시간 상한, 본문·조치·한계의 금지 형식.
- 쉼표 유무를 허용한 **정확한 숫자 경계**. 1,000이 21,000 또는 1,000,000에 포함된 것으로 통과하지 않는다.
- `scoped`로 상수원/친수활동 설명을 나눠 해당 구간의 숫자와 일부 부등호를 검사한다.
- 필수/금지 문구와 정규식, 조치 5개 초과·완전 중복·6번 이상 반복 번호 목록.
- 출처 번호 0 및 근거 수를 넘는 번호, 개념/되묻기 경로의 불필요한 출처·조치, 근거가 있는데 근거를 부인하는 문구.
- 기대 문서·PDF 쪽이 **본문/조치/한계에서 실제 번호로 인용**되었는지 확인한다. `evidence`에만 들어 있는 것으로는 통과하지 않는다. 기대 쪽 목록 중 하나 이상을 인용하면 통과한다. D10의 기대 쪽은 2026-11-02에 PDF 8쪽(시행령 별표2, 환경부장관 또는 시·도지사)을 추가했다. 35쪽의 수행체계와 다른 층위의 맞는 근거이기 때문이다. 문서 범위가 PDF 5~51쪽으로 넓어진 뒤 사람이 결정했다.
- 지점 시나리오의 구조화 관측/예측 수치, 주중 날짜의 월요일 정규화, 미확인 구간 안내, 수계별 지점 목록.
- 실제 조회 행과 프롬프트 **관측 구획**에 기준일 뒤 관측이 들어갔는지 확인한다. 다음 주 예측 대상일이나 지침 발행일은 누출로 오인하지 않는다. 저장 예측의 `input_until <= base`와 `target_date = base + 7일`도 확인한다.

## 반드시 별도로 검토할 것

자동 통과는 정답 보증이 아니다. 각 문항의 `review`도 함께 본다.

- 구간 안에서 **관심/경계/해제라는 단계와 수치·부등호가 정확히 연결되는지**. 현재 구간별 문자열 검사는 단계별 모든 관계를 해석하지 않는다.
- 기대 쪽을 인용했더라도 각 주장과 관리조치가 그 근거에서 실제로 뒷받침되는지.
- 현재와 미래, 관측과 예측, 모델 구간과 실제 공식 발령을 혼동하지 않는지. 발령을 긍정하는 단정뿐 아니라 미발령 단정도 검토한다. 금지 정규식은 모든 한국어 표현을 포괄하지 않는다.
- 수온 상승·세포수 증가 같은 추세와 원인 설명이 실제 최근 관측과 맞는지. 현재 스크립트는 모든 추세 문장을 자동 판정하지 않는다.
- 저장되지 않은 q20/q80/95% 신뢰구간을 만들어내지 않는지. 구조화 값이 null인 것만으로 자연어 날조가 없다고 보장할 수 없다.
- 없는 연도에 과거 행을 현재 자료처럼 해석하지 않는지. 관측 날짜가 기준일 이전이어도 너무 오래된 자료면 별도 문제다.
- 잘못된 전제를 정정했는지. "녹조류의 일종이 아닙니다"처럼 금지 문자열이 부정문에 쓰인 경우는 오탐일 수 있다.
- 공식 발령 표 6, 예측 단계 표, 정수장 조치가 뒤섞이지 않는지.

자동 판정과 수동 검토를 나눠 기록한다. 검사를 느슨하게 바꿔 통과 수를 올리지 않는다. 기준을 바꾸면 사유와 해시를 남기고 별도 실행 결과로 보존한다. LLM 채점은 넣지 않았다.

## 검사 명령

```bash
cd backend
source .venv/bin/activate
ruff check .
ruff format --check .
pytest
```

프론트는 이 작업에서 변경하지 않지만 전체 확인에는 `frontend`에서 `npm run lint && npm run build`도 사용한다. 커밋은 사용자가 직접 한다. 원본 데이터·평가 결과·개인 학습 기록을 커밋하지 않는다.

## 일부러 망가뜨린 결과 비교 시연

2026-11-01 실제 실행의 D01 통과 응답을 한 문항만 복사해 비교용 참조 파일을 만들고, 복사본의 경계 하한 `10,000`을 `100,000`으로 바꾸었다. 기대 조건은 유지하고 `check`로 다시 판정했다. **합성 오류 파일은 모델이 새로 생성한 실제 응답이 아니다.** 원본 실행 결과는 수정하지 않았다.

```bash
python3.11 backend/scripts/eval_regression.py --compare \
  data/eval/comparison_demo_reference.json \
  data/eval/comparison_demo_degraded.json
```

`통과 1/1 -> 0/1`, `나빠짐 D01`, `수치누락:10,000`, `구간수치:상수원:10,000 누락/오배치`가 표시된다. 출력은 `data/eval/comparison_demo.txt`에 보존했다.

## 호출 경계

이번 생성 평가는 요청서대로 `build_answer`를 직접 호출한다. 지점·기준일은 질문 파일의 `location`, `base_date`를 전달하므로, `/api/chat`의 질문에서 지점을 추출하는 처리·요청 검증·대화 로그 저장·브라우저 표시까지 검사하는 것은 아니다. API의 기존 동작은 백엔드 전체 테스트로 확인했으며, 향후 UI에서 실제 사용 흐름까지 검증하려면 별도 시나리오가 필요하다.
